# Lessons

## 2026-10-27

- 分支命名必须结合项目实际约定：功能开发使用 `feat/...`、修复使用 `fix/...`、重构使用 `refactor/...`、文档使用 `docs/...`；发版分支使用 `release-vX.Y.Z`，不使用 `codex/` 前缀。
- 每个开发分支只对应一个 PR。开始开发前先获取最新 `main` 并从该提交创建分支；本地开发和验证经维护者认可后，才推送远端、创建 PR 和合并。
- 多个 PR 必须逐个合并；每合并一个后等待 `main` CI 通过，后续分支先同步最新 `main`。
- 版本发布按积累的改动形成版本；构建产物、发布产物或安装链路修复合入后立即发布 patch。
- npm 一键安装方案先按双渠道设计：npm registry 作为新增安装入口，GitHub Release tarball 继续保留；未确认市场索引消费者前，不直接替换现有 curated schema。
- 需求范围可在 Spec 阶段调整；本次从 A（仅 npm 包）改为 C（npm + DSH 一键安装 + GitHub 兼容入口）。
